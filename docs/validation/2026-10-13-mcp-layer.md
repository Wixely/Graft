# The MCP layer, and the API hole it exposed

Recorded: 2026-10-13. Owner: Implementation agent. Decision: [ADR 0008](../decisions/0008-mcp-layer.md).

## What was built

`src/Graft.Mcp`, a separate executable speaking the Model Context Protocol over stdio, offering ten tools
that call Graft's ordinary HTTP API with a personal access token.

And the two API routes it needed, which did not exist: `PUT /api/v4/projects/:id` for visibility, and
`PUT /api/graft/projects/:id/page` for the curated page.

## Why not DnaX, which the request named

DnaX ships MCP packages and they were read at the pinned commit before any of this was written.

`DnaX.MCPFab` is an application template rather than a library. `McpFabHost.CreateBuilder` creates its own
`WebApplication`, binds its own Kestrel listener, replaces the static Serilog logger, installs its own
configuration chain, registers its own default authentication scheme and owns the process exit code. There
is no entry point that accepts a host which already exists. Taking it would make Graft an MCPFab server
rather than give Graft an MCP layer, and it costs roughly twenty runtime assemblies.

`DnaX.RemoteAccess.Mcp` is the right shape, twenty-four lines, and the two calls it makes are the official
SDK's own API. What it adds is `DnaX.RemoteAccess`'s own SQLite-backed token store, a second answer to who
is calling, beside the one Graft already has.

The official SDK is therefore the smaller dependency, not a substitution for one: DnaX's own MCP package
depends on it and adds to it. The DnaX reading was still worth doing, because its build policy encodes
failures that are invisible until a trimmed binary misbehaves, and those are followed here.

## Why a separate process

Graft.Server publishes NativeAOT and that is a release claim. Nobody involved has AOT-published an MCP
library: DnaX verifies trimmed and single-file behaviour with a real smoke test, has never run
`PublishAot`, and its build props say `IsAotCompatible` stays off until something actually does. The forge's
dependency closure is therefore unchanged by any of this.

It also means the server can be pointed at a Graft that is already running, and an operator who wants no
agent access simply runs nothing.

## NativeAOT, measured rather than assumed

| Check | Result |
| --- | --- |
| Build with `IsAotCompatible`, AOT, trim and single-file analyzers, reflection JSON off | clean, no warnings |
| `dotnet publish -p:PublishAot=true` | reaches the native linker, stops on the absent C++ workload |

The analyzers earned their place during this work. A generic `JsonArray.Add<T>` reflects over its argument
to build a value, and the build failed on `IL2026` and `IL3050` until it was changed to the `JsonNode`
overload. That is precisely the class of fault that works under a debugger and dies in a trimmed binary.

ILC never runs on this machine, the same environmental gap as everywhere else in this repository, so the
native binary's runtime behaviour remains unverified.

## Evidence

The Git, API and browser suite is **389 assertions**, up from 372. Accounts is 129 and operations 41, both
unchanged and passing.

The new assertions cover the two routes from the outside, with a token and no browser:

- A token changes visibility, the route reports what it set, and the change persists.
- A token publishes and withdraws a page, and the state reads back.
- A `read_api` token is refused with an insufficient-scope error rather than a missing-project error,
  because a credential's own scope is not a secret about somebody else's project.
- Another account's token gets the same 404 as a project that does not exist, so concealment is unaffected.
- An anonymous caller is refused.
- `internal`, an unsupported property, and an empty body are each refused by name rather than ignored.

The MCP server itself was driven over stdio against a live Graft, with certificate verification on and the
server's own certificate supplied as the trusted root:

```
initialize -> {'name': 'graft', 'version': '1.0.0'}
tools/list -> 10 tools
```

Read-only, the default: `graft_browse` returned the public listing, and `graft_set_visibility` refused with
`This Graft MCP server is read-only ... An operator can restart it with --allow-writes true.`

With writes allowed, the full loop: create a project, make it public, publish its page, read it back with
`page_published` true, and find it in the anonymous public listing. Every step through an MCP tool call.

## The tools

Reads: `graft_list_projects`, `graft_get_project`, `graft_browse`, `graft_list_branches`,
`graft_list_commits`, `graft_list_tree`, `graft_read_file`.

Writes, refused unless `--allow-writes true`: `graft_create_project`, `graft_set_visibility`,
`graft_set_page_published`.

`graft_browse` returns the anonymous view deliberately, so it never reveals a private or unlisted project
even though the token could see some of them. `graft_read_file` refuses a file that is not UTF-8 rather
than returning replacement characters, because a tool that says a binary file is text teaches the agent
something false and the next thing it does with that is wrong.

## Running it

```
Graft.Mcp --server <https origin> --token-file <path> [--allow-writes true|false] [--ca-certificate <path>]
Graft.Mcp --licences
```

The token is read from a file and never taken on the command line, matching `Graft.Admin bootstrap`: a
command line is visible to every process on the machine and lands in shell history. There is no option to
skip certificate verification; `--ca-certificate` names the certificate to trust instead, which also covers
a forge using a private authority.

## What this does not cover

Streamable HTTP transport. Only stdio is wired up, which is what a local MCP client launches directly. An
HTTP-reachable MCP endpoint needs an authentication story of its own.

Writing repository content. There is no tool that commits, pushes or edits a file. Git already does that
well over a transport the agent can drive directly, and a half-implemented write path through MCP would be
the worse of two options.

Anything about the browser routes, which still require a session cookie, a CSRF header and a matching
origin. The token routes are additional, not a replacement, and the browser's CSRF invariant is untouched.
