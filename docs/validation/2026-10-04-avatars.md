# Avatar evidence

Date: 2026-10-04. Owner: Implementation agent. Review when the accepted image formats, the image validator, the avatar storage schema, or the serving headers change.

## Result

Users and projects can have avatars. They are uploaded through the browser transport, validated, stored in the database, and served back with a GitLab-compatible `avatar_url` on the user and project payloads, which is null when none is set.

Storage is a SQLite table rather than files on disk. Avatars are small by policy, so this means a backup captures them atomically with the accounts and projects they belong to, and a restore cannot reinstate one without the other.

## Schema upgrade

Migration 2 adds the `Avatars` table. The **upgrade path was exercised**, not just fresh creation: a database was created with the previous build, then opened with the new one. The `Avatars` table appeared, both migrations were recorded in the ledger, and the existing account survived. Fresh-database creation is covered by the acceptance suites.

## Validation approach, and what it does not give you

The plan called for decoding and re-encoding each image. That would require an imaging library, and the one in common use for .NET now ships under a split licence with commercial terms. Rather than take that dependency quietly, `ImageContent` parses the container to confirm the bytes really are PNG, GIF, JPEG or WebP and reads the declared dimensions, refusing anything it cannot positively identify.

**This is a weaker guarantee than re-encoding and should not be described as making an image safe.** It bounds what reaches a decoder; it does not certify content. What it does cover is the risk that actually matters for an avatar, which is a file a browser decides to treat as markup:

- SVG is never accepted, so no script can be stored as an avatar.
- The served content type is the one the validator determined, never one the client supplied.
- The existing `X-Content-Type-Options: nosniff` header stops reinterpretation.

If pixel-level sanitising is wanted later, it is a licence decision rather than an engineering one.

## Checks

Acceptance (`tests/Graft.Acceptance`, 66 to 92 assertions): PNG, GIF and JPEG recognised with correct dimensions; SVG, arbitrary text, an empty file, a truncated PNG, an over-dimension image and an overlong file all refused; a large image round-tripping byte-for-byte; replacement overwriting the previous avatar; a user unable to set another user's avatar; a non-member unable to set a project avatar, with nothing stored on refusal.

Over HTTP, against a live server: setting a real 365 KB PNG returned `204`; `GET` returned `200` with `Content-Type: image/png` and bytes **identical to the source file**; `HEAD` returned the same headers with no body; `If-None-Match` returned `304`; unauthenticated access returned `401`; a text file and an SVG were both refused with `400`. Verified in Chromium end to end, with the image rendering at 1254 × 1254 in both the profile header and the top bar.

## A Dapper.AOT limitation worth knowing

Dapper.AOT binds a byte array by expanding it into one SQL variable per element, which is how it supports `IN` clauses and cannot express a BLOB. A 350 KB image became 350,000 variables and SQLite refused the statement with "too many SQL variables". A `DbValue` attribute pinning `DbType.Binary` does not change that decision, so the single avatar write uses a provider command; reading the column back through Dapper is fine. All 43 other storage call sites remain intercepted with no reflection fallback. The acceptance suite keeps a deliberately large image as the regression guard.

## Boundaries

- Structural validation only, as above. No decode, no re-encode, no EXIF stripping.
- Accepted formats are PNG, GIF, JPEG and simple lossy or lossless WebP. Extended WebP, which can carry animation and alpha chunks, is refused.
- Limits are 2 MB encoded and 4096 pixels on a side.
- **The API side is not implemented.** GitLab's avatar upload is multipart, and `POST /api/v4/projects/:id/uploads` does not exist here. These are explicit deviations recorded in [compatibility.md](../compatibility.md), not claimed support.
- `avatar_url` presence costs one keyed existence check per payload. Project listings are capped at 100 and already do heavier per-project work, so this was not optimised.
- Avatars are visible to any authenticated user for user avatars, and to anyone who may browse the project for project avatars. There is no separate avatar visibility rule.
