# GitLab conformance plan

Recorded: 2026-09-18. Updated: 2026-09-19. Status: bounded REST and browser subsets implemented; GitLab 18.0.0 source fixture passes for project creation, while reference-instance and existing-client runs remain pending. Owner: Implementation agent. Review: 2026-09-25 and before each selected upstream API-version change.

Confirmed goal: GitLab APIs/URL conventions and GitLab-style apps, with most GitLab functionality. Exact GitLab versions/editions and clients remain TBD. Reference for research: [official REST documentation](https://docs.gitlab.com/api/rest/). Recheck official documentation before implementing a versioned contract.

| Surface | Evidence to record | Current status |
| --- | --- | --- |
| REST | Method/path, request/response/error shape, auth, scopes, pagination, encoding, status codes, redirects | Bounded read/write subset passes the C# harness; GL-004 has a version-matched source fixture, while live upstream comparison remains pending |
| GraphQL | Supported schema/queries/mutations, pagination and authorization | Not implemented |
| Browser/raw/archive URLs | Namespace nesting, refs, filenames, downloads, canonical redirects | Personal namespace project/deep-link route implemented; any branch can be browsed and chosen as the default; a public or unlisted project is browsable with no account; raw/archive and nesting pending |
| Git HTTPS/SSH and LFS | Clone/fetch/push, auth and ref permissions, large-object integrity | Bounded Git HTTPS subset passes, including anonymous clone and fetch of a public or unlisted repository; SSH and LFS pending |
| OAuth/tokens/webhooks | Token lifecycle/scopes, application flows, payloads, auth and delivery/retry behavior | Bounded personal access-token creation/list/revoke is implemented; OAuth and webhooks are not |
| CI configuration | Includes/templates, stages/jobs, expressions, variables, artifacts, caches, environments | Not implemented |
| Runner protocol | Enrollment/polling/jobs/logs/artifacts/cancellation separately from CupriNet transport | Not implemented |
| CLI/SDK/MCP clients | Host configurable, pinned client version, concrete end-to-end workflows | `glab` 1.58.0 API auth/user/list/create/read passes against Graft. Graft hosts its own MCP endpoint at `/mcp` behind `--mcp true`, with a stdio launcher `src/Graft.Mcp` for local clients, both over the same REST API; see [ADR 0009](decisions/0009-mcp-in-the-forge.md). Graft also addresses a project by an instance-wide slug at `/projects/<slug>`, which GitLab has no equivalent for and which is additive to the `owner/slug` and numeric-id forms; see [ADR 0010](decisions/0010-project-slugs.md). GitLab SDKs remain candidates |

Each future matrix row should record upstream version, requirement source, fixture, implementation status, last tested date, build identifier, expected result and known deviation. A path match without behavior/auth fidelity is not compatibility. Distinguish imported CI files from executable pipeline compatibility.

The current workflow covers authenticated user/project discovery, read-only repository REST calls and Git HTTPS clone/push. The acceptance client is a C# `HttpClient` harness plus Git 2.53.0.windows.2. Pin and run an existing GitLab-style client before claiming client compatibility.

## Proposed MVP fixture baseline

MVP-06 update: [repository UI and API evidence](validation/2026-09-19-mvp06-repository-api-ui.md) demonstrates product namespace routing, HTTPS/token authentication, durable storage and the selected REST reads. This is implementation evidence against rolling official documentation, not a version-matched GitLab compatibility result.

Provisional version candidate: **GitLab CE 18.0.0, REST v4**. This remains an agent-proposed baseline rather than a user-selected deployment version. The GL-004 fixture pins the official unified repository tag `v18.0.0-ee`, commit `504fd9e5236e13d674e051c6b8a1e9892b371c58`, and hashes the tagged documentation, endpoint source, request specs, authentication and scope documentation. See [source-fixture evidence](validation/2026-09-19-gitlab-18-source-fixture.md). All seven creation cases later passed a disposable [GitLab CE 18.0.0 reference](validation/2026-09-19-gitlab-18-live-reference.md), and pinned `glab` 1.58.0 workflows passed against that reference.

Client evidence: installed **Git 2.53.0.windows.2** provides actual transport interoperability. Pinned **glab 1.58.0** passes `auth login` plus `api user`, project list, project create and project read against both the GitLab reference and Graft; see [pinned-client evidence](validation/2026-09-19-glab-graft.md). A C# HttpClient harness verifies additional wire/error behavior independently. GitlabMCPSharp remains a later client candidate. No broad glab support is implied.

The read rows marked **implemented** were first tested by the 64-assertion MVP-06 harness. The GitLab 18.0 project-creation fixture raised that workflow to 87 assertions, user/membership raised it to 97, and personal access-token lifecycle raised it to 107. Account credentials raised it to 135, and server-authored commits raise the current Windows JIT workflow to 165; the NativeAOT comparison is pending a machine with the C++ build tools. GL-004 is driven by the pinned 18.0.0 source fixture; the other rows still reference rolling official documentation. Git transport uses protocol v0/SHA-1. The live GitLab CE 18.0.0 and pinned `glab` 1.58.0 reports establish the exact bounded reference/client result described above.

Any other encoding is refused by name | [Git HTTP](https://git-scm.com/docs/http-protocol) |

| GL-010 | `avatar_url` on user and project payloads | **Implemented subset:** the field is present and null when no avatar is set, otherwise an absolute URL to a Graft-served image. | GL-011 | Avatar upload | **Not implemented.** GitLab accepts an avatar as multipart form data on `PUT /api/v4/user` and `POST /api/v4/projects/:id`; Graft has no multipart handling and uploads avatars only through its browser transport | [Projects](https://docs.gitlab.com/api/projects/) |
| GL-012 | `POST /api/v4/projects/:id/uploads` | **Not implemented.** Deliberately left unclaimed so the path stays available; Graft's browser uploads live under `/api/graft/uploads` instead | [Projects](https://docs.gitlab.com/api/projects/) |
| GL-014c | `GET /api/v4/projects/:id/repository/commits/:sha/diff` | **Implemented:** the files a commit touched, with hunks and per-line detail, plus `parent` to choose a side of a merge. Requires Developer-equivalent browse access, never a published-page grant, because a diff prints file contents. **Deviation:** Graft returns its own richer shape rather than GitLab's flat `diff` strings | [Commits](https://docs.gitlab.com/api/commits/) |
| GL-016 | `GET`/`POST`/`PUT`/`DELETE /api/v4/projects/:id/members` | **Implemented subset:** list, grant and revoke by `username` and a Graft role of `reporter`, `developer` or `maintainer`. Requires the `api` scope and Maintainer-equivalent access, so reading the membership is itself a management act and a read-only token cannot enumerate it. **Deviation:** GitLab identifies members by `user_id` and grades them by numeric `access_level`; Graft has three named roles and takes a username. Invitations, expiry and inherited membership are not implemented | [Members](https://docs.gitlab.com/api/members/) |
| GL-014b | `POST`/`PUT /api/v4/projects/:id/repository/files/:file_path` | **Implemented:** writes one file and commits it, with the content in the request as `text` or `base64`. Requires the `api` or `write_repository` scope and Developer-equivalent access, the same rules a git push obeys. **Deviation:** GitLab distinguishes creating a file from updating one and refuses the wrong verb; Graft commits what it was given either way. Deleting a file is not implemented | [Repository files](https://docs.gitlab.com/api/repository_files/) |
| GL-015 | `PUT /api/v4/projects/:id` | **Implemented subset:** `visibility` (`private`, `unlisted`, `public`), `name`, `description` and `default_branch`; any combination may be sent and only what is sent is changed. Requires the `api` scope and Maintainer-equivalent access; every other attribute, `path` included, is refused by name rather than ignored, so this route never moves a project. GitLab accepts dozens of attributes here, all of which remain explicit deviations. The scope is checked before the project is resolved, so an insufficient scope answers `403` while an inaccessible project still answers `404` | [Projects](https://docs.gitlab.com/api/projects/) |
| GL-013 | Anonymous read of a public project | **Implemented subset:** with `--public-browsing true`, `GET /api/v4/projects/:id`, `/repository/tree`, `/repository/commits`, `/repository/branches` and `/repository/files/:path` answer a caller presenting no token when the project's visibility is `public` or `unlisted`. A token that does not resolve stays a `401` rather than being treated as anonymous. GitLab's instance-wide `internal` visibility has no equivalent | [Projects](https://docs.gitlab.com/api/projects/) |
| GL-014 | `GET /api/v4/projects` listing for an anonymous caller | **Not implemented.** The authenticated listing still returns only projects the caller owns or is a member of, and never the public set. Graft's own `GET /api/browse` serves discovery instead, under its own path and shape | [Projects](https://docs.gitlab.com/api/projects/) |
| GL-017 | `DELETE /api/v4/projects/:id` | **Implemented:** removes the project, its membership, its collaboration and its repository, immediately. Requires the `api` scope and the project's owner or an administrator, which is stricter than GitLab, where a Maintainer suffices. **Deviation:** GitLab answers `202 Accepted` because its deletion is scheduled; Graft's is complete when the response is written, so it answers `204 No Content`. There is no recycle bin, no restore and no deferred-deletion period | [Projects](https://docs.gitlab.com/api/projects/) |
| GL-018 | `GET`/`POST /api/v4/projects/:id/issues` and `GET`/`PUT .../issues/:iid` | **Implemented subset:** title, description, state and author, with `iid` numbered from one per project and `state` filtering on `opened`, `closed` or `all`. `state_event` takes `close` or `reopen`. Reading needs the `api` or `read_api` scope and whatever reading the repository needs, so a public project's issues are readable anonymously; writing needs `api` and membership. **Deviation:** editing text or changing state needs the author or Maintainer-equivalent access, where GitLab allows any Developer. Labels, milestones, assignees, due dates, confidentiality and every other attribute are not implemented and are refused by name | [Issues](https://docs.gitlab.com/api/issues/) |
| GL-019 | `GET`/`POST /api/v4/projects/:id/issues/:iid/notes` and the same under `merge_requests` | **Implemented subset:** an author, a body and a time, listed oldest first. No system notes, no editing, no replies and no resolvable threads. Deletion exists under Graft's own browser route rather than GitLab's `DELETE .../notes/:id` | [Notes](https://docs.gitlab.com/api/notes/) |
| GL-020 | `GET`/`POST /api/v4/projects/:id/merge_requests`, `GET`/`PUT .../:iid`, `GET .../:iid/changes` | **Implemented subset:** source and target branch, title, description, state, `merge_status` and `merge_commit_sha`. Both branches must exist when a proposal is created, and the branches cannot be changed afterwards. `changes` compares from the merge base and returns Graft's own richer diff shape, the same one GL-014c uses, rather than GitLab's flat `diff` strings. **Deviation:** a listing always reports `merge_status` as `unchecked` because deciding costs three tree walks per row; read one proposal to get a decided answer. Graft adds `merge_method` and `conflicts`, which GitLab has no equivalent for. Approvals, reviewers, draft state, squash, rebase and cross-project proposals are not implemented | [Merge requests](https://docs.gitlab.com/api/merge_requests/) |
| GL-021 | `PUT /api/v4/projects/:id/merge_requests/:iid/merge` | **Implemented subset:** fast-forwards when the target is an ancestor of the source, otherwise writes a merge commit, and requires the permission a push requires. `should_remove_source_branch` is honoured. **Deviation:** Graft refuses with `409` when both branches changed the same file and names those files, because it does not merge file contents; GitLab resolves many of those cases. It also refuses with `409` while approvals are outstanding. `merge_commit_message`, `squash` and `merge_when_pipeline_succeeds` are not implemented | [Merge requests](https://docs.gitlab.com/api/merge_requests/) |
| GL-022 | `POST`/`DELETE /api/v4/projects/:id/repository/branches` | **Implemented:** points a new branch at a branch, tag or commit id, and removes one. Requires the `api` scope and Developer-equivalent access, the same rules a push obeys. **Deviation:** creating a name that already exists is `409` rather than moving it, and deleting the branch the project opens at is refused with `409`; GitLab's protected-branch rules have no equivalent here. `MERGE /repository/merged_branches` is not implemented | [Branches](https://docs.gitlab.com/api/branches/) |
| GL-023 | `POST`/`DELETE /api/v4/projects/:id/merge_requests/:iid/approve` and `unapprove` | **Implemented subset:** one approval per person, recording the commit approved. Requires the `api` scope and the permission to push, which is stricter than GitLab, where any member with access may approve. **Deviation:** an approval stops counting when the source branch moves and is reported with `current: false`, where GitLab keeps it unless the project opts out; an author cannot approve their own proposal; the required count is a single project-wide number set through `POST /projects/:id/approvals` with `approvals_before_merge`. Approval rules, approver groups, code owners and `approvals_required` per rule are not implemented | [Merge request approvals](https://docs.gitlab.com/api/merge_request_approvals/) |
| GL-025 | `GET`/`POST`/`DELETE /api/v4/projects/:id/repository/tags` | **Implemented subset:** list, create and delete. A listing reports `target`, the object the reference names, and `commit`, what that resolves to, so an annotated tag pushed by a client is described correctly. Creating requires the `api` scope and Developer-equivalent access. **Deviation:** tags created through Graft are lightweight only, because an annotated tag's message and tagger belong to a release and releases are not implemented; `GET .../tags/:name`, release notes on a tag and protected tags are absent | [Tags](https://docs.gitlab.com/api/tags/) |
| GL-026 | `GET /api/v4/projects/:id/repository/files/:file_path/raw` | **Implemented:** the file's exact bytes, with the path as one URL-encoded segment, which is GitLab's own documented form. **Deviation:** always `application/octet-stream` with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, never a content type derived from the file. Repository content cannot be rendered on the origin that holds the session cookie and the API; see [ADR 0017](decisions/0017-getting-things-out.md). A browser therefore saves a raw file rather than previewing it, and a command-line client is unaffected | [Repository files](https://docs.gitlab.com/api/repository_files/) |
| GL-027 | `GET /api/v4/projects/:id/repository/archive[.tar.gz\|.zip]` | **Implemented subset:** the whole tree at a revision, as a gzipped tar or a zip, under one directory named for the project and the short commit, carrying the executable bit. The same attachment and content-type rules as GL-026 apply. **Deviation:** two formats rather than GitLab's four, no `path` parameter to archive a subdirectory, and the archive is built in memory, which is bounded only because the Git engine bounds a repository | [Repositories](https://docs.gitlab.com/api/repositories/) |
| GL-024 | `GET`/`POST`/`DELETE /api/v4/projects/:id/hooks` | **Implemented subset:** a URL, a signing secret and a set of `push`, `issue`, `merge_request` and `comment`, available only on a server started with `--webhooks true`; the routes are absent otherwise. Requires the `api` scope and Maintainer-equivalent access. **Deviation:** Graft signs each delivery as `X-Graft-Signature`, an HMAC-SHA256 of the body, where GitLab sends the secret itself in `X-Gitlab-Token`; the payload is Graft's own small shape rather than GitLab's; the event set is four rather than a dozen; and editing a hook, instance-wide hooks, redelivery and test deliveries are not implemented | [Project hooks](https://docs.gitlab.com/api/projects/#hooks) |

Git HTTPS token authentication needs its own GitLab-version fixture; API header acceptance does not prove Git credential compatibility. REST unknown routes must return an explicit API error, never the Blazor HTML fallback. Treat unsupported query fields deliberately: document version-matched ignore/reject behavior instead of silently claiming full endpoint support.

## Graft-specific routes

These are Graft's own surface, not GitLab compatibility. They live under `/api/graft/` so they cannot collide with a GitLab path, and they exist because the browser needs capabilities the REST surface does not yet offer. An API client should not depend on them.

| Route | Purpose |
| --- | --- |
| `/api/graft/uploads/**` | Browser upload transport; see [ADR 0005](decisions/0005-browser-upload-transport.md) |
| `POST /api/graft/admin/import/inspect` | Reference inventory and exclusion report for an uploaded Git bundle |
| `POST /api/graft/projects/:id/repository/files` | Commit uploaded files to a branch |
| `GET`, `HEAD`, `POST /api/graft/avatars/{user|project}/:id` | Serve and set avatars |
| `POST /api/projects/:id/default-branch` | Choose which branch a project opens at |
| `POST /api/projects/:id/owner` | Transfer project ownership |
| `DELETE /api/projects/:id` | Delete a project, confirmed by sending its path |
| `GET /api/graft/admin/audit` | Read the audit trail; administrators only |
| `/api/projects/:id/issues/**` and `/api/projects/:id/merge-requests/**` | The browser's collaboration surface, mirroring the GitLab-compatible routes with session and CSRF authentication instead of a token |
| `POST`, `DELETE /api/projects/:id/branches` | The browser's branch management |
| `POST /api/projects/:id/approvals` | Set how many approvals a merge needs |
| `/api/projects/:id/hooks` | The browser's webhook management, present only with `--webhooks true` |
| `/api/projects/:id/tags` | The browser's tag management |
| `GET /api/projects/:id/raw/**` | One file as bytes, for a browser session; the GitLab-shaped route answers a token only |
| `GET /api/projects/:id/archive[.tar.gz\|.zip]` | The same archive, for a browser session |

The collaboration routes exist twice on purpose. The `/api/v4` family answers a token and the `/api/projects`
family answers a browser session with an Origin and CSRF check; the body of each operation is one shared
function, so a rule cannot hold on one surface and not the other. An API client should use the `/api/v4`
family, which is the one this matrix describes.

GitLab owns `/uploads/...` and `/api/v4/projects/:id/uploads`. Neither is served by Graft's upload group, and both remain available for later compatibility work.

Deferred surfaces remain not implemented: GraphQL, most write-side project/repository REST APIs beyond creation and the bounded edits above, raw/archive routes, SSH/LFS, OAuth, CI/runner protocol, webhooks, nested groups and complete browser URL conventions. Repository-only import via an ordinary push preserves Git content; it is not a GitLab data migration. [The backlog](backlog.md) carries the full list with reasoning.
