# GitLab conformance plan

Recorded: 2026-09-18. Updated: 2026-09-19. Status: bounded REST and browser subsets implemented; GitLab 18.0.0 source fixture passes for project creation, while reference-instance and existing-client runs remain pending. Owner: Implementation agent. Review: 2026-09-25 and before each selected upstream API-version change.

Confirmed goal: GitLab APIs/URL conventions and GitLab-style apps, with most GitLab functionality. Exact GitLab versions/editions and clients remain TBD. Reference for research: [official REST documentation](https://docs.gitlab.com/api/rest/). Recheck official documentation before implementing a versioned contract.

GitLab SDKs remain candidates |

Each future matrix row should record upstream version, requirement source, fixture, implementation status, last tested date, build identifier, expected result and known deviation. A path match without behavior/auth fidelity is not compatibility. Distinguish imported CI files from executable pipeline compatibility.

The current workflow covers authenticated user/project discovery, read-only repository REST calls and Git HTTPS clone/push. The acceptance client is a C# `HttpClient` harness plus Git 2.53.0.windows.2. Pin and run an existing GitLab-style client before claiming client compatibility.

## Proposed MVP fixture baseline

MVP-06 update: [repository UI and API evidence](validation/2026-09-19-mvp06-repository-api-ui.md) demonstrates product namespace routing, HTTPS/token authentication, durable storage and the selected REST reads. This is implementation evidence against rolling official documentation, not a version-matched GitLab compatibility result.

Provisional version candidate: **GitLab CE 18.0.0, REST v4**. This remains an agent-proposed baseline rather than a user-selected deployment version. The GL-004 fixture pins the official unified repository tag `v18.0.0-ee`, commit `504fd9e5236e13d674e051c6b8a1e9892b371c58`, and hashes the tagged documentation, endpoint source, request specs, authentication and scope documentation. See [source-fixture evidence](validation/2026-09-19-gitlab-18-source-fixture.md). All seven creation cases later passed a disposable [GitLab CE 18.0.0 reference](validation/2026-09-19-gitlab-18-live-reference.md), and pinned `glab` 1.58.0 workflows passed against that reference.

Client evidence: installed **Git 2.53.0.windows.2** provides actual transport interoperability. Pinned **glab 1.58.0** passes `auth login` plus `api user`, project list, project create and project read against both the GitLab reference and Graft; see [pinned-client evidence](validation/2026-09-19-glab-graft.md). A C# HttpClient harness verifies additional wire/error behavior independently. GitlabMCPSharp remains a later client candidate. No broad glab support is implied.

The read rows marked **implemented** were first tested by the 64-assertion MVP-06 harness. The GitLab 18.0 project-creation fixture raised that workflow to 87 assertions, user/membership raised it to 97, and personal access-token lifecycle raised it to 107. Account credentials raised it to 135, and server-authored commits raise the current Windows JIT workflow to 165; the NativeAOT comparison is pending a machine with the C++ build tools. GL-004 is driven by the pinned 18.0.0 source fixture; the other rows still reference rolling official documentation. Git transport speaks smart HTTP protocol versions 0 and 2 over SHA-1 repositories; see GIT-001 to GIT-004. The live GitLab CE 18.0.0 and pinned `glab` 1.58.0 reports establish the exact bounded reference/client result described above.

| GIT-001 | `GET /:namespace/:project.git/info/refs?service=git-upload-pack` and `git-receive-pack` | **Implemented:** auth before disclosure, correct service responses, refs and empty repository. The version 0 advertisement carries `multi_ack_detailed`, `ofs-delta`, `include-tag`, an agent and the `HEAD` symref, and peeled `^{}` lines for annotated tags. A client sending `Git-Protocol: version=2` receives the version 2 capability advertisement for `git-upload-pack`; `git-receive-pack` has no version 2 and is answered in version 0 whatever the header says. [ADR 0028](decisions/0028-git-engine.md) | [Git HTTP](https://git-scm.com/docs/http-protocol), [protocol v2](https://git-scm.com/docs/protocol-v2) |
| GIT-002 | `POST /:namespace/:project.git/git-upload-pack` | **Implemented:** clone and fetch through Git 2.55.0.windows.5 over protocol version 0 and version 2. Negotiation honours haves: each known have is acknowledged as common, `ready` is said once every want reaches a common commit, and the pack carries only what the client lacks, delta-compressed with offset deltas when the client accepts them. Version 2 answers `ls-refs` (prefixes, `peel`, `symrefs`, `unborn`) and `fetch` (`want`, `want-ref`, `have`, `done`, `ofs-delta`, `include-tag`, `thin-pack` accepted) with the pack on sideband one. `Content-Encoding: gzip` is accepted and decompressed; the size ceiling applies to the decompressed bytes. **Deviation:** `deepen`, `shallow` and `filter` are refused by name, so there are no shallow or partial clones; thin packs are accepted from the client's side but never sent; any other content encoding is refused by name | [Git HTTP](https://git-scm.com/docs/http-protocol), [protocol v2](https://git-scm.com/docs/protocol-v2) |
| GIT-003 | `POST /:namespace/:project.git/git-receive-pack` | **Implemented:** initial and incremental push, branches and tags, token auth, stale ref and interrupted publication checks. A push that leaves more than 1,000 loose objects is repacked before it is answered, as Git runs `gc --auto`. **Deviation:** protocol version 0 only, which is the only version a push has; deleting a reference by push is refused, because branch and tag deletion is a decision on the forge ([ADR 0015](decisions/0015-review-journey.md)) | [Git HTTP](https://git-scm.com/docs/http-protocol), [pack format](https://git-scm.com/docs/pack-format) |
| GIT-004 | Repository on disk | **Implemented:** a bare Git repository Git itself opens: zlib loose objects under `objects/xx/`, packs with version 2 indexes under `objects/pack/`, `packed-refs` with peeled lines, `HEAD` and `config`. The index Graft writes is byte-identical to the one `git index-pack` writes for the same pack. The layout Graft used before 2026-10-29 converts itself the first time a repository is opened. **Deviation:** SHA-1 only; Graft is the only writer and reads the packs it wrote; no bitmaps, commit-graph or multi-pack index; nothing is pruned | [Git repository layout](https://git-scm.com/docs/gitrepository-layout), [pack format](https://git-scm.com/docs/pack-format) |

| GL-016 | `GET`/`POST`/`PUT`/`DELETE /api/v4/projects/:id/members` | **Implemented subset:** list, grant and revoke by `username` and a Graft role of `reporter`, `developer` or `maintainer`. | GL-014d | `DELETE /api/v4/projects/:id/repository/files/:file_path` | **Implemented:** commits the removal of one file from `branch` with `commit_message`, taken from a JSON body or from the query string, and answers `204`. GitLab accepts dozens of attributes here, all of which remain explicit deviations. The scope is checked before the project is resolved, so an insufficient scope answers `403` while an inaccessible project still answers `404` | [Projects](https://docs.gitlab.com/api/projects/) |
| GL-013 | Anonymous read of a public project | **Implemented subset:** with `--public-browsing true`, `GET /api/v4/projects/:id`, `/repository/tree`, `/repository/commits`, `/repository/branches` and `/repository/files/:path` answer a caller presenting no token when the project's visibility is `public` or `unlisted`. | GL-018 | `GET`/`POST /api/v4/projects/:id/issues` and `GET`/`PUT .../issues/:iid` | **Implemented subset:** title, description, state, author, `labels` (comma-separated on write, an array on read, with `label_details` carrying colours), `add_labels`, `remove_labels`, `milestone_id` (zero clears), `assignee_usernames`, `due_date` (empty clears), `confidential` and `time_stats`; `iid` numbered from one per project. [ADR 0020](decisions/0020-planning.md) | [Issues](https://docs.gitlab.com/api/issues/) |

| GL-032 | `PUT /api/v4/projects/:id/merge_requests/:iid/rebase` | **Implemented subset:** rewrites the source branch onto the target's tip, replaying each commit as a three-way merge of its own change and refusing by name where a file was changed on both sides or where the branch holds a merge commit. ## Graft-specific routes

These are Graft's own surface, not GitLab compatibility. They live under `/api/graft/` so they cannot collide with a GitLab path, and they exist because the browser needs capabilities the REST surface does not yet offer. An API client should not depend on them.

| Route | Purpose |
| --- | --- |
| `/api/graft/uploads/**` | Browser upload transport; see [ADR 0005](decisions/0005-browser-upload-transport.md) |
| `POST /api/graft/admin/import/inspect` | Reference inventory and exclusion report for an uploaded Git bundle |
| `POST /api/graft/projects/:id/repository/files` | Commit uploaded files to a branch |
| `GET`, `HEAD`, `POST /api/graft/avatars/{user|project}/:id` | Serve and set avatars |
| `POST /api/projects/:id/default-branch` | Choose which branch a project opens at |
| `POST /api/projects/:id/owner` | Transfer project ownership |
| `DELETE /api/projects/:id` | Delete a project, confirmed by sending its path |
| `GET /api/graft/admin/audit` | Read the audit trail; administrators only |
| `/api/projects/:id/issues/**` and `/api/projects/:id/merge-requests/**` | The browser's collaboration surface, mirroring the GitLab-compatible routes with session and CSRF authentication instead of a token |
| `POST`, `DELETE /api/projects/:id/branches` | The browser's branch management |
| `POST /api/projects/:id/approvals` | Set how many approvals a merge needs |
| `/api/projects/:id/hooks` | The browser's webhook management, present only with `--webhooks true` |
| `/api/projects/:id/tags` | The browser's tag management |
| `GET /api/projects/:id/raw/**` | One file as bytes, for a browser session; the GitLab-shaped route answers a token only |
| `GET /api/projects/:id/archive[.tar.gz\|.zip]` | The same archive, for a browser session |

The collaboration routes exist twice on purpose. The `/api/v4` family answers a token and the `/api/projects`
family answers a browser session with an Origin and CSRF check; the body of each operation is one shared
function, so a rule cannot hold on one surface and not the other. An API client should use the `/api/v4`
family, which is the one this matrix describes.

GitLab owns `/uploads/...` and `/api/v4/projects/:id/uploads`. Neither is served by Graft's upload group, and both remain available for later compatibility work.

Deferred surfaces remain not implemented: GraphQL, most write-side project/repository REST APIs beyond creation and the bounded edits above, raw/archive routes, SSH/LFS, OAuth, CI/runner protocol, webhooks, nested groups and complete browser URL conventions. Repository-only import via an ordinary push preserves Git content; it is not a GitLab data migration. [The backlog](backlog.md) carries the full list with reasoning.
